# 04 即時反応と指示処理

「指示を聞かない」「判断が遅い」「とっさに反応しない」は、次の3つに分けられる。

- **反射層がない**（攻撃・溶岩・落下に、計画とは独立して反応する仕組みがない）
- **指示が実行されるまでの経路が長い**（LLMを最低2往復する）
- **指示が途中で捨てられる規則がある**

## 現在の指示処理の流れ

1. `ServerChatEvent`（優先度LOWEST、`bep_3davater_companion.java:115-121`）→ `server.execute` → `NpcChatRouter.receive`。
2. 受け手は12ブロック以内で視線が通るNPCに限られる（`PlayerChatPolicy.recipients`）。グループへの依頼は最初の1体だけが受ける（`NpcChatRouter.java:33-40`）。
3. `NpcMind.hearPlayer`（`:606-619`）は文脈を固定し、`playerChats` に追加する（最大4件、古い順に破棄）。
4. `tickPlayerChat`（`:641-745`）の処理:
   - 会話セッションを開く（Codex `thread/start`）。
   - 要求枠を待つ。
   - `{speech, taskComplete, instruction}` で1往復する。
   - 条件を満たせば `npc.setInstruction(...)` を呼ぶ。
5. `setInstruction` → `mind.instructionChanged` → `stop()`（`:772-790`）:
   - epochを進める。
   - 作業・発言・**会話**のセッションをすべて閉じる。
   - **`playerChats` を消去する**（`:787`）。
6. 次のTickで新しい計画セッションを開き、TaskPlanを1往復で作る。形式が誤っていれば修復のためにもう1往復する（`CodexBridge.java:320-345`）。
7. `LocalTaskRunner` を生成し、毎Tick実行する。

**定型の指示を手元で解釈する処理はない。** 「止まって」「ついてきて」もLLMを通る。`LocalActionPolicy` は指示の分類器ではなく、行動候補を順位付けするモデル。

## 遅延の原因

| 原因 | 箇所 | 値 |
| --- | --- | --- |
| サーバー全体で1つの要求枠。全NPCの会話・計画・定期発言・完了発言が取り合う | `NpcService.java:137-141`、`CodexConfig.java:25` | 3秒間隔 |
| 1指示に最低2往復（会話→計画）。`stop()` で会話セッションを閉じるので、次の会話は開き直しから | `NpcMind.java:785` | ― |
| 高度な計画は `effort:"high"` | `CodexBridge.java:422` | Neo環境の実測で26〜31秒（`Docs/NpcNeoDiamondInvestigation20261026.md`） |
| 固定の待ち時間 | `NpcMind.java:404,537`（+60Tick）、`:346,370`（+100Tick）、`:468,588`（**エラー後+600Tick＝30秒**）、会話エラー（+200Tick） | ― |
| ストリーミングなし。待ち時間の上限が長い | `HttpBrain.java:286,298` `"stream", false`、`turnTimeoutSeconds=180` | ― |
| 再計画は失敗が確定してから | `LocalTaskRunner.java:283,290`（失敗3回、空振り32回、回収待ち40回）。その後 `NpcRecoveryQueue` でさらにLLM | ― |
| 順位付けモデルの計算（未計測） | 56→1419→1419→1、5専門家、候補1つあたり約210万回の積和 | `microDeadline` 750µs は最初の判断の後にしか見ていない（`LocalTaskRunner.java:254-256`） |

## 指示が捨てられる規則

1. **返答時点での話者確認**（`NpcMind.java:728-732`）。LLMの返答が届いた時点でプレイヤーが12ブロック以上離れている、次元が違う、視線が通らない、のいずれかなら、返答も指示も**通知なしで捨てる**。文脈は受信時に固定済みなので、この再確認は不要。
2. **後続の発言による上書き**（`:739` `latestOwnerChat > last`）。所有者が後に何か言うと（「急いで」「聞いてる？」など）、前の指示は捨てられる。後の発言から指示が出なければ、指示そのものが失われる。
3. **`stop()` が `playerChats` を消去する**（`:787`）。指示が確定した瞬間に、待ち行列にあった他の発言も消える。
4. **LLMだけが分類する。** プロンプトは「挨拶・雑談・質問・進捗確認」に空の指示を返すよう求めている（`:689-697`）。「〜してくれる？」のような依頼は質問と誤分類されやすい。
5. **作業完了で追従を解除する**（`NpcMind.java:232` `setFollowsOwner(false)`）。追従は指示が空のときだけ動く（`NpcSkills.java:746`）。作業が終わるたびにその場に留まるので、「ついてきて」を聞かなくなったように見える。
6. **保留状態が続く。** `replans > 2` で `announceBlock()` した後は、新しい指示が来るまで毎Tick何もしない（`:372-375`）。
7. **水中安全の実行中は思考を丸ごと止める**（`CompanionEntity.java:357` `if (!waterSafety.tick()) mind().tick()`）。会話の処理も止まる。
8. AIが無効なときや接続に失敗したときは、会話から何も実行できない（`NpcMind.java:95-98`）。

## 反射層の現状

| 既存 | 内容 | 不足 |
| --- | --- | --- |
| `NpcWaterSafety` | 毎Tick、空気までのBFSで退避。最優先 | これだけが本当の反射 |
| `NpcLocalWorld.tactics`（`:116-130`） | `getLastHurtByMob()` が6ブロック以内の敵で視線が通るとき、`attack` を候補に加える | 学習モデルの候補の1つで、作業の候補に負けることがある。`pending` 中（長い技能の実行中）は評価されない |
| `eat` 候補 | 満腹度12以下で候補に加える | 同上 |
| `NpcExpedition` | 体力6未満・炎上・溶岩で中止（退避はしない） | ― |

**ないもの:**
- 指示がないときの防御。`HurtByTargetGoal` も近接攻撃のGoalもない（`CompanionEntity.java:143-147`）。`hurtServer` にもフックがない。
- 溶岩・火・落下・窒息・低体力・クリーパー・矢への反応。
- 所有者の防衛。

## 改善案

### 1. 反射層 `NpcReflexes`（最優先）

`CompanionEntity.tick` の `waterSafety.tick()` の隣で毎Tick評価する。ルールのみで、LLMも学習モデルも呼ばない。

| 優先 | 条件 | 行動 |
| --- | --- | --- |
| 1 | 溺水（既存の `NpcWaterSafety`） | 空気へ退避 |
| 2 | 溶岩・火の中、または足元が溶岩 | 最寄りの安全なブロックへ移動。水があれば使う |
| 3 | 落下中、または進行方向が奈落・高所の縁 | 移動停止、後退 |
| 4 | 体力が少ない | 食事。敵が近ければ後退してから |
| 5 | 3〜4ブロック以内でクリーパーが着火 | 離れる |
| 6 | 自分か所有者を攻撃した敵 | 武器へ持ち替えて反撃。盾があれば防御 |
| 7 | 矢が飛んでくる | 横へ移動、盾 |

- 発火中は、`NpcSkills` と `LocalTaskRunner` を**一時停止**する（取り消さない）。解除後は元の技能を再開する。
- 発火と解除はジャーナルに `reflex_start` / `reflex_end` として記録する。
- 指示がないときのために、バニラの `HurtByTargetGoal` 相当、所有者防衛、近接攻撃のGoalも `CompanionEntity.java:143-147` へ追加する。
- `mind().tick()` を止めるのは、移動の衝突を避けるのに必要な部分だけにする。会話の受信は反射中も続ける。

### 2. （不採用）定型指示の即時処理

キーワードによる指示の即時処理は、会話の一部を指示と取り違える誤動作の恐れがあるため採用しない（2026-10-26、利用者の判断）。指示の解釈はLLMに任せ、3〜5と8で往復の回数と待ち時間を減らす。

### 3. LLMの往復を1回にする

- `NpcBrain.Reply` には既に `plan` がある（`NpcBrain.java:10`）。会話の1往復でTaskPlanまで返させる。
- `stop()` では会話セッションを閉じない（`:785`）。取り消すのは実行中の作業ターンだけにする。セッションを開いたまま使い回す。

### 4. 指示を捨てる規則の修正

- 返答時の距離・視線の再確認（`:728-732`）をやめる。
- 「上書き」は、後の返答が実際に指示を生んだときだけにする（`:739`）。
- `instructionChanged` から呼ぶ `stop()` では `playerChats` を消去しない（`:787`）。
- 作業完了時は、作業前の追従状態に戻す（`:232`）。

### 5. 要求の優先度

`NpcService.requestSlot` を「NPCごと・用途ごと」の枠に分ける。所有者の指示と計画は、定期発言に待たされない。指示の処理中は定期発言を止める。エラー後の30秒待ち（`:468,588`）は、2秒から始める指数的な待ちにする。

### 6. 実行中の中断

- `LocalTaskRunner.tick` は `pending` 中でも緊急の候補（防御・食事）だけは評価する（`:250`）。
- 長い技能（`NpcToolQueue`、`NpcLongTravel`、`NpcConstruction`、`NpcExpedition`）は毎Tick `interruptRequested()` を確認する。
- 防御・食事は学習モデルの点数（`:332`）ではなく、ルールの固定優先度で選ぶ。

### 7. ローカルでの再計画を先に行う

段階が失敗したら、LLMへ戻す前に、別の対象・別の立ち位置・近傍の探索を試す。最初の失敗の時点で次の計画の要求を非同期に始めておけば、LLMが必要になったときの待ちが短くなる。

### 8. ストリーミングと待ち時間の上限

- `stream:true` にして、`speech` が届いた時点で発言する。
- 会話の待ち上限は約20秒、計画は別の値にする。
- `effort:"high"` は明示的な復旧のときだけにする。キーワードで高度な計画に切り替える処理（`NpcPlanningTier`）は、これに合わせて見直す。

### 9. 指示と計画のキャッシュ

正規化した指示と状況のハッシュをキーに、検証済みのTaskPlanを保存する。同じ指示の繰り返しではLLMを呼ばない（`NpcExecutionMemory` と同じ考え方）。

## 実施結果（2026-10-26）

### 反射層 `NpcReflexes`（改善案1の最小構成）

- `CompanionEntity.tick` で、溺水回避の次に毎Tick評価する。発火中は計画した作業（`mind().tick()`）を一時停止する。取り消しはしない。
- **反撃**: 次の条件をすべて満たす敵（`Enemy`）に、所持武器で近接攻撃する。
  - 直近100Tick以内に、NPCか所有者を攻撃した。
  - 8ブロック以内にいて、視線が通る。
- **反撃の終了**: 次のいずれかで終える。
  - 敵が倒れた。
  - 12ブロックより離れた。
  - 200Tick経った。
  - NPCの体力が6未満になった。
- 計画された attack / hunt / guard / defeat の実行中（直近20Tick）は、反射層は動かない。
- **溶岩・火**: 体が溶岩か火の中にあれば、周囲4ブロック内で燃えない最寄りの床へ走る。水があれば水を優先する。最大60Tick。
- ジャーナルに `reflex_start` / `reflex_end` を記録する。
- **未対応**: 落下・クリーパー・矢・低体力時の後退・盾。指示がないときの `HurtByTargetGoal` 相当は、この反撃で代わりにした。

`NpcReflexGameTests` の結果:

| 試験 | 反射層なし | 反射層あり |
| --- | --- | --- |
| 指示なしでゾンビに殴られる | 600Tickの間ゾンビが生存（失敗） | 倒す |
| 所有者がゾンビに殴られる | 600Tickの間ゾンビが生存（失敗） | 倒す |
| 溶岩の穴（5×5、床より1段低い）に沈む | 脱出する | 脱出する |

溶岩の試験は、バニラの浮上動作でも脱出できるため差が出ない（3×3の穴での計測では、反射層ありは21Tick・体力13.5、なしは29Tick・体力9.5）。回帰の確認用として残した。

### 指示を捨てる規則の修正（改善案4）

- 返答が届いた時点の距離・視線・次元の確認をやめた。発言者がオフラインのときだけ捨てる。
- 後続の発言で上書きされた指示は、捨てずに保留する（`instruction_deferred`）。
  - 後続の返答が新しい指示を返せば、そちらを採用する。
  - 指示を返さなければ、保留した指示を実行する（`instruction_resumed`）。
- 指示が確定しても、会話セッションと待ち行列の発言を消さないようにした（`stop(false)`）。
  - 会話側の世代は `chatEpoch` に分けた。
  - 送信後に、GUIなどで別の指示が設定された場合は、その返答の指示を採用しない。
- 作業完了時に、所有者が設定した「待機中の追従」を解除しないようにした。

`NpcChatOrderGameTests`（返答を試験側で遅らせる模擬AIを使用）の結果:

| 試験 | 修正前 | 修正後 |
| --- | --- | --- |
| 返答待ちの間に所有者が13ブロック以上離れる | 指示が設定されない（失敗） | 指示が設定される |
| 返答待ちの間に「急いで」と追加で発言する | 指示が設定されない（失敗） | 指示が設定される |

## 目標とする応答時間

| 種類 | 現在（推定） | 目標 |
| --- | --- | --- |
| 被弾→反撃 | 長い技能の終了まで反応しない | 1〜2Tick |
| 「止まって」 | 会話LLM1往復＋要求枠＋計画（数秒〜十数秒） | LLM1往復（ストリーミングで数秒） |
| 「ついてきて」 | 同上。完了後に追従が切れる | 同上、完了後も維持 |
| 採集の依頼 | 2往復＋高度計画で20〜60秒 | 1往復。同じ指示はキャッシュで即時 |
