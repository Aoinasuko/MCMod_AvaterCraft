# 05 周辺情報の取得（葉に囲まれた原木・水中の位置）

## 現在の観測

## 葉に囲まれた原木を掘れない原因

1つの不具合ではない。「葉は不透明・固体・立てない」とする判定が、複数の段階で重なっている。

1. **視線判定が衝突形状を使う。** `visibleHitFrom` は `ClipContext.Block.COLLIDER`（`NpcSkills.java:330`）。葉は完全な衝突箱を持つので、目と原木の7つの標本点の間に葉が1枚あれば「見えない」になる。`mine()` は「掘れないか見えない」で失敗し（`:1506`）、`dig` の接近（`:905-909`）も「見える採掘位置がない」で失敗する。
2. **立ち位置の探索が葉を拒否する**（`NpcLocalWorld.approach`、`:1099-1145`）。
   - 候補は原木から水平±2、**高さ-1〜+1**だけ。樹冠の高い位置の原木には候補がない。
   - 立つセルとその上に衝突形状がないことを要求する（`:1113-1114`）。葉のあるセルは候補にならない。「葉を除いてから立つ」という選択肢がない。
   - 支持面に `isFaceSturdy(UP)` を要求する（`:1115`）。葉の支持形状は空なので、葉の上には立てない。一方、`NpcWalkSurface.standable`（`:199-215`）は衝突形状で判定するので、葉の上に立てる。**同じ「立てるか」の判定が食い違っている。**
   - 視線も同じ衝突形状のレイで確認する（`:1131`）。
3. **障害物を除く前に候補から外す。** `mineAccessible`（`NpcLocalWorld.java:236-238`）は「4以内で見える」か「`approach()` が見つかる」を要求する。そのため、囲まれた原木は候補の段階で消える。足元より低い原木も除外する（樹冠の上に立った場合など）。
4. **届く距離を足元から測る。** `permitted` は `npc.distanceToSqr(atCenterOf(pos)) <= d²`（`NpcSkills.java:294`）。足元から3.5上・水平2の原木は約4.03で、上限4を超える。バニラの届く距離は目から約4.5。
5. **作業経路 `goal=mine` の代替処理も弱い。**
   - `ready()`（`NpcWorkRoute.java:496-503`）は、立ち位置が原木以下の高さ、√12以内、中心1本のレイ（`rayObstacle`、`:465-478`）を要求する。
   - 障害物を除く処理（`:589-594`）は準備完了の位置でしか動かず、最初に当たった1ブロックしか対象にしない。
   - `mayBreak` は流体に接するブロックを壊さない（`:390-393`）。
   - `stable` は原木の上に立つことを禁じる（`:348`）。
   - 足場資材の調達中は作業経路を使わない（`NpcLocalWorld.java:671`）。
6. **試験が易しい。** 葉の試験 `NpcWorkRouteGameTests.leaves`（`:182-215`）は、地面の高さに葉の殻を置いた3段の原木。NPCと原木が同じ高さなので通る。頭より上の幹を樹冠が囲む状況の試験はない。

### 修正案

1. **葉を考慮した視線判定。** `obstructionsTo(target)` を追加する。`ClipContext.Block.OUTLINE` でレイを飛ばし、葉に当たったら記録して先へ進む。真偽値ではなく「遮っている葉の一覧」を返す。
2. **障害物を除く下位行動。** 遮っているのが `BlockTags.LEAVES`（または植物などの柔らかい自然ブロック）だけなら、届く葉から順に `dig` して、原木を掘り直す。`NpcSkills` の `dig` 処理（`:905-925`）と `mineAccessible` に入れ、候補から先に消さない。
3. **届く距離を目から測る。** `getEyePosition()` から4.5で判定する（`:294`、`:1506`）。
4. **立ち位置の探索を書き直す**（`approach`）。
   - 高さ-3〜+1を探す（下から上の原木を掘る）。
   - 葉のあるセルは「除去コスト付きで立てる」とする。
   - 支持面は `NpcWalkSurface` と同じ衝突形状の判定にする。
   - 戻り値は「候補＋除去コスト」にする。
5. **対象の順位付け。** `find_blocks` の結果を3D距離ではなく接近コストで並べる。露出した原木、幹の最も低い原木、支持のある立ち位置を優先する。`NpcSpatialObservation` の資源に、遮る葉の数（露出度）を加える。

最も効くのは1〜3。高い木は「下から順に掘り、届かなくなったら1段積んで登る」のがプレイヤーの基本で、それを「低い原木を優先＋葉を除く」で再現できる。

### 実施結果（2026-10-26）

- **届く距離**: 目の位置から4.5ブロック（プレイヤーと同じ）で判定する（`NpcSkills.withinReach`）。`mine` と `dig` の接近判定で使う。
- **葉を考慮した視線判定**: `leafObstruction` を追加した。
  - 目から原木の中心と6面の点へレイを飛ばす。
  - 遮っているのが葉（`BlockTags.LEAVES`）だけなら、最も近い葉を返す（最大6層）。
  - 葉以外のブロックが途中にあれば null を返す。
- **葉の除去**: `mine` で原木が見えず、葉だけが遮っている場合は、届く範囲の葉をプレイヤーと同じ破壊速度で掘る（`clearLeaf`）。視線が通ったら原木を掘る。
- **候補の判定**: `mineAccessible` は「届いて、見えるか葉だけが遮っている」を受け入れる。
- **立ち位置の探索**（`approach`）:
  - 高さを-4〜+1まで探す。
  - 頭より上のブロックだけ、立ち位置の目から4.5で判定する。それ以外は従来どおり、足元の中心から2ブロック以内に立つ。
  - 葉だけが遮る位置も候補に入れる。
  - 当初はすべてのブロックを目から4.5で判定していた。このとき `cooperative_empty_hands_diamond_storage` が10回中7回失敗した（変更前は0/10）。原因は、ブロックから離れた立ち位置まで候補になったこと。二分探索で特定して上記の条件に改めたあと、10回中0回の失敗になった。
- 新しいGameTest `canopy_enclosed_trunk_from_the_ground`: 6段の幹のうち高さ3〜7を葉が囲む。足場ブロックは持たせない。
  - 修正前: 4,000Tickの間に回収できず失敗。
  - 修正後: 6本すべてを回収する。
- **未対応**: 葉のセルを「除去すれば立てる」立ち位置として扱うこと。`NpcWorkRoute.ready` の1本のレイ。

## 水中・水際の位置を把握できない原因

1. **呼吸の判定がバニラと違う**（`NpcWaterSafety.breathing`、`:19-23`）。
   - 目のセルの水の高さが目のY以下なら「呼吸できる」とする。
   - バニラ（`updateFluidOnEyes`）は目のYから0.111引いた位置で判定する。
   - そのため水面直下の0.11ブロックでは、NPCは「呼吸できる」と判断する一方、実際には空気が減り続ける。水面付近で緊急状態が早く解除され、入り切りを繰り返す。
2. **水柱の判定が「深い」と「不明」を区別せず、天井も見ない**（`NpcWaterTravel.column`、`:103-113`）。
   - 足元のx/zの1列だけを見て、深さは安全深度+1まで数える。5を超えると `known=false` になる。
   - 水面の上が空気かを確認しない。氷の下・張り出しの下・蓋のある水では、「水面」は実際には天井になる。`danger()`（`NpcWaterSafety:27`）は浅い既知の水と判断し、空気が120以下になるまで待つ。
   - `current()`（`:114-116`）は足元のセル（`blockPosition()`）を使うので、上下に揺れるたびに結果が変わる。
3. **浅瀬を歩く状態が存在しない。**
   - `standable` は支持面か体の位置に流体があれば拒否する（`NpcWalkSurface.java:287,322`）。水没したハーフブロック・階段、海草、岸の深さ1〜2の水が該当する。
   - `swimmable` は水面のセルだけを扱い、足を水面の0.4下に置く（`NpcWaterTravel.java:134`）。深さ1の水の底に立っているNPCは、実際より0.49上にいるものとして扱われる。
   - `NpcLocalWorld.dangerous`（`:590-596`）と `NpcWorkRoute.harmful`（`:333`）は流体をすべて禁止する。作業経路は水を使えない。
4. **深い水で `standingCell` が壊れる**（`NpcWalkSurface.java:224-235`）。水柱が不明だと水のセルを返す。地形観測の起点に床がなくなり、`reachable` が空になる（`NpcSpatialObservation:203-205`）。**岸を探す必要があるまさにそのときに、歩ける場所が何も見えなくなる。**
5. **水中の状態が計画LLMに届かない。** 水中か、足下の深さ、水面までの距離、最寄りの空気や岸を送っていない。深い水は投影で `~` にまとめられる。
6. **陸から水への移行が成立しない**（`Docs/NpcWaterPoolStudy20261026.md` と一致）。プールの試験では3件とも一度も入水していない。`NpcWaterTravel.transition`（`:145-151`）は、泳げるセルがグラフに入った後でしか使われない。作業経路は流体を通れない。橋材は土・丸石・石など6種で木材を含まず、足場の木材を使えない。
7. **使われていないコード。** `waterWalking`（`NpcSkills.java:1373-1404`）はどこからも呼ばれていない。

### 修正案：WaterState

`NpcWaterTravel` に、毎Tick1回計算する状態を追加する。

```java
record WaterState(
    boolean eyeSubmerged,     // npc.isEyeInFluid(FluidTags.WATER)（バニラと同じ判定）
    boolean feetInWater,
    boolean wading,           // 接地していて水中
    int depthBelowFeet,       // 32まで数える。「深い」と「不明」を分ける
    int depthToSurface,
    boolean surfaceOpenAir,   // 水面の上が空気か（氷・天井の判定）
    BlockPos nearestAir,      // NpcWaterSafety.search のBFSを再利用
    BlockPos nearestShore,
    Vec3 current) {}
```

- `breathing`、`danger`、`standingCell`、`observe()` はこれを使う。
- `NpcWalkSurface.standable` に「浅瀬」の判定を加える。支持面が固体、足の位置の水が1ブロック以下、頭が空気中なら立てる。
- 深い水では `standingCell` が水面のセルを返し、そこから泳ぎの辺で岸へつながるようにする。地形観測が空にならない。
- 計画LLMへの観測に `water: {submerged, depth_below, to_surface, open_air, shore:[x,y,z], air:[x,y,z]}` を加える。
- `NpcWorkRoute.harmful` は「流体の隣を掘ると流れ込むか」を量で評価し、すべての流体を禁止するのはやめる。
- 橋材に板材・原木など、所持している固体ブロックを加える。

### 呼吸判定の実施結果（2026-10-26）

- `NpcWaterSafety.breathing` を、バニラが空気を減らす判定と同じ `isEyeInFluid(FluidTags.WATER)` にした。
- 水関連のGameTest（water / swim / air を含む18件）は成功した。
- WaterState とボクセル分類の統一は未着手（07を参照）。

## ボクセル分類の統一

`NpcSpatialObservation` の4分類をやめ、次の分類のグリッドを1つ作る。経路探索・接近位置・作業経路・観測が同じものを参照する。

| 分類 | 例 | 経路での扱い |
| --- | --- | --- |
| `solid` | 石、土、原木 | 支持面。通行不可（作業経路なら掘削コスト） |
| `soft_breakable` | 葉、草、ツタ | 通行不可だが除去コストは小。視線は条件付きで通す |
| `climbable` | はしご、ツタ、足場 | 垂直の辺 |
| `fluid_shallow` | 深さ1〜2の水 | 浅瀬を歩く辺 |
| `fluid_deep` | 深さ3以上の水 | 泳ぐ辺（空気までの距離で制限） |
| `hazard` | 溶岩、火、粉雪、ベリー | 溶岩・火は禁止、その他はコスト |
| `air` | 空気 | 通行可 |
| `unknown` | 未ロード | 探索しない |

計画用の投影には、NPCのいる高さの水平断面を加える。樹冠や水中の層が見えるようにする。

## 優先順

1. 葉を考慮した視線判定、目からの届く距離（小規模、効果大）
2. 葉を除く下位行動、`mineAccessible` の順序の修正
3. WaterState と浅瀬の立てる判定
4. `approach` の書き直し、到達コストによる対象の順位付け
5. ボクセル分類の統一（01の WorldModel / NavigationService と同時に）
