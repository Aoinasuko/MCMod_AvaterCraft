# 02 経路探索の正確性

## 現在の仕組み

- `CompanionEntity` は `PathfinderMob`。移動制御は `NpcStepMoveControl`、経路追従は `NpcGroundNavigation`（`GroundPathNavigation` の派生。ドア開閉・浮上は有効）。
- 経路は独自の逐次A*（`WalkingPathSearch.java`）。範囲は各軸128、最大65,536ノード、8方向、1歩の高低差は -1/0/+1 のみ（`:88`）。コストは直進10・斜め14、高低差1ごとに+4。地形や壁際のコストはない。
- 予算は `NpcWalkingRoute.poll()` の1回512ノード／0.75ms、サーバー全体で1Tick 4,096ノード／2ms（`:92-98`）。240Tickで探索を打ち切る（`:79`）。
- 結果はバニラの `Path` に変換して `NpcGroundNavigation` で追従する。5Tickごとに先の6ノードを再検査する（`validAhead`、`NpcSkills.java:1292`）。
- 呼び出し元は `NpcSkills.walking`（move_to / move_precisely）、`NpcFollowing`、`NpcWorkRoute`（24ノードごとに分割）、`NpcLongTravel`（112ブロックの区間）。`NpcExpedition` と `dig` の接近はバニラの `createPath` を使う。

## 不正確になる原因

### A1. 動く生物を壁として固定する（最重要）

`NpcWalkingRoute.Terrain` の構築時に、半径128以内の生物（最大256体：所有者、動物、敵）を取得する。NPCの幅だけ膨らませ、探索が終わるまで**通行不可のセルとして固定する**（`NpcWalkingRoute.java:227-245`、`compute()` の `occupied` 判定 `:263`）。

- かつて生物がいた場所を迂回する、不自然な経路になる。
- 目標地点に生物（所有者など）が立っていると、終点が除外され、即座に `UNREACHABLE` になる。
- `validAhead` も近傍8ブロックで同じ判定をする。前方6ノードを誰かが横切るたびに停止→再探索になり、最終的に「繰り返し変化した」失敗で終わる。

**修正:** 生物を `occupied` から外す。所有者は常に除外する。N Tick以上静止している生物だけ、周囲のセルにコストを加える。`validAhead` では生物を無視するか、次の2ノード上で静止している生物だけを対象にする。

#### 実施結果（2026-10-26）

**変更内容**

- 探索開始時に生物がいたセルは、通行不可ではなく**コスト+40**（約4ブロック分の迂回）にした（`NpcWalkingRoute.Terrain.penalty`）。
  - `WalkingPathSearch.Terrain` に `penalty(Cell)` を追加した（既定値0）。
  - 斜め移動では、かすめる両側のセルのコストも加える。斜めに角をすり抜けて生物に接触しないようにするため。
- 迂回路があれば静止した生物を避ける。迂回路がなければ、そのセルを通る経路を作る（生物は移動する前提）。
- `validAhead` / `validPoints` / `landing` は生物を取得しないようにした。前方を横切る生物で経路を捨てなくなった。
- 目的地のセルは従来どおりコストなし（`allowed`）。
- 所有者だけを特別扱いする処理は入れていない。所有者もほかの生物と同じコストで扱う。静止時間の判定も入れていない。

**新しいGameTest（`NpcActorRouteGameTests`）**

| 試験 | 修正前 | 修正後 |
| --- | --- | --- |
| 囲いの唯一の隙間に牛が立っている（40Tick後に去る） | 失敗: `No supported walking route within 128 blocks` | 成功 |
| 7頭の牛が経路を往復して横切る | 失敗: 再探索5〜7回、または `Walking path repeatedly changed or became blocked` | 成功（再探索2回以下） |
| 直線上に静止した牛 | 成功 | 成功（中心間距離0.9超で横を通る） |

**回帰**

- GameTestは135件すべて成功した。全件の実行を2回行い、2回とも成功。
- JUnitは205件で、スキップ15件、失敗0件。
- `tall_tree_builds_walkable_stairs` は15回実行し、15回とも成功した。

**残り**

- `avoidStationaryActor`（03のB5）が目標への直線上の生物で誤発火する問題は未修正。
- 追従の終点の許容（A5）も未修正。

### A2. 落下・ジャンプの移動がない

近傍の高低差は -1/0/+1 だけ（`WalkingPathSearch.java:88`）。`NpcWaterTravel.java:58` でも1.25ブロックを超える段差を拒否している。プレイヤーなら飛び降りる2〜3ブロックの段差で、大きく迂回するか経路なしになる。

**修正:** 最大3ブロックの落下を辺として加える（1ブロックごとにコスト+2。落下ダメージが出ない範囲）。1マスの隙間を飛び越えるジャンプ辺も、必要なら後から加える。

### A3. 流体をすべて壁として扱う

- `NpcWalkSurface.clearBody` は体の位置に空でない流体があれば拒否する（`:382`）。`standable` も支持面の流体を拒否する（`:347`）。
- 水没したハーフブロック・階段・フェンス、海草、水たまりの縁が通れない。
- 水は「深さ5以下の泳げる水面」としてのみ通れる（`NpcWaterTravel.java:43`）。
- `NpcGroundNavigation.moveTo` は、経路のどこかに深さ5超または深さ不明の水があると、経路全体を取り消す（`:28-30`）。

**修正:** 足元の1ブロック以下の浅い水を「歩いて渡れる」状態として認める（頭が空気中で、支持面が固体の場合）。深さ6以上は「泳ぐ辺」として高いコストを付ける。経路全体の取り消しはやめる。詳細は05を参照。

### A4. はしご・ツタ・足場ブロックを使えない

`NpcWalkSurface.height()` は中心の下に衝突箱を要求する（`:265-271`）。そのため登れるブロックが「立てる場所」にならない。

**修正:** `BlockTags.CLIMBABLE` を垂直の辺として加える（上下1マスごと、コスト12程度）。

### A5. 終点の許容がない

- move_to の終点は `List.of(target)`（`NpcSkills.java:1337`）で、`terrain::stand` を通る必要がある（`NpcWalkingRoute.java:46`）。LLMが指定したYが1ずれている、終点がブロックや流体、生物のいるセルである、のいずれでも即 `UNREACHABLE` になる。`canonicalTarget` が補正するのは半ブロックだけ。
- 追従も同様。終点は所有者と同じブロックYで `distSqr<=2` のセルに限られる（`NpcFollowing.java:61`）。所有者が階段やハーフブロックの端、ジャンプ中のときは、終点がほぼなくなる。
- 既存資料でもチェストのセルを終点にして失敗した例がある（`Docs/NpcArchitectureReview20261025.md` の2章）。

**修正:** `NpcWalkingRoute.to(target, p -> p.distSqr(target) <= 2 && |dy| <= 1)` のように、終点を集合として渡す。move_precisely だけは厳密にする。追従は |dy| ≤ 2、半径2まで許す。

#### 実施結果（2026-10-26）

**move_to の終点**（`NpcSkills.walking`）

- 指定セルに立てる場合は、従来どおりそのセル1つを終点にする。
- 立てない場合（ブロックそのもの、床の1段上の空中など）は、周囲のセルを終点にする。
  - まず指定セルに面で接する6方向のセル（下の床、横、上）を探す。
  - 1つも立てなければ、距離√2以内（斜めの隣）まで広げる。
- 到着後は経路の終点を新しい目標にする（従来のチェストの扱いと同じ方式）。
- 成功時の結果に `requestedTarget`（元の指定座標）を付け、計画AIが補正に気づけるようにした。
- move_precisely（`_arrival`）は従来どおり厳密に指定セルへ向かう。

**追従の終点**（`NpcFollowing`）

- 所有者のブロックから高さ±1・水平半径2以内を終点にした。
- 従来は「同じ高さで距離√2以内」だった。
- 案では高さの許容を±2としていたが、崖の下などの誤った終点を避けるため±1にした。

**新しいGameTest（`NpcArrivalGameTests`）**

| 試験 | 修正前 | 修正後 |
| --- | --- | --- |
| 石の柱（ブロックそのもの）を move_to で指定 | 失敗: `pathSearchNodes:0` で即 `No supported walking route` | 成功（柱の隣に立つ） |
| 床の1段上の空中を指定 | 同上 | 成功（直下の床に立つ） |
| 所有者が地面から1.2上にいる（ジャンプ中・段差の縁を想定） | 2,400Tickの間、到達できない | 成功 |

回帰の結果は03のB5と合わせて記載する（GameTest 139件を2回実行し全件成功、JUnitは205件・スキップ15件・失敗0件、`tall_tree_builds_walkable_stairs` は15回中15回成功）。

### A6. 中継点の追従が厳しく、詰まりの検出が働かない

- グリッド経路の次ノードへ進む条件が、ノード中心から**0.2ブロック以内**（`NpcGroundNavigation.java:40-42`）。バニラは「幅の半分程度」で、角を省略できる。経路の平滑化もないので、8方向のジグザグのたびに中心へ寄る。速度が上がると行き過ぎて戻る（揺れ）。
- `NpcWaterTravel.follow()` が**毎Tick** `navigation.moveTo(path, …)` を呼ぶ（`NpcWaterTravel.java:90`。呼び出し元は `NpcSkills.java:1366`、`NpcFollowing.java:282`）。バニラの `moveTo` は呼ぶたびに `lastStuckCheck` を初期化するので、**バニラの詰まり検出が一度も発火しない**。trimPath と水の走査も毎Tick実行される。

**修正:**
- 0.5ブロック以内、またはノードを通り過ぎた（経路方向への射影が正）ら進める。
- 糸引き法で平滑化する。NPCからノードi+2まで体の掃引が通り、平坦ならi+1を飛ばす。
- `moveTo` は経路オブジェクトが変わったときだけ呼ぶ。
- 40Tick動かなければジャンプか再探索、という短い詰まり規則を、20秒の監視（`NpcMoveProgress.STALL_TICKS=400`）より前に置く。

#### 実施結果（2026-10-26）

- `NpcWaterTravel.follow` が、同じ経路で毎Tick `moveTo` を呼んでいたのをやめた。経路が変わったときだけ呼び、それ以外は速度だけを更新する。これでバニラの詰まり検出が働く。
- 中継点の判定（0.2）は変えていない。斜めの長距離のダッシュを計測したところ、プレイヤーの100%で揺れによる減速がなかったため。
- 40Tickでジャンプか再探索する短い詰まり規則は未実装。B7と合わせて行う。

### A7. 壁沿いの経路になる

コストに「壁からの距離」がないので、最短経路は壁・角・木に沿う。引っ掛かりやすく、後述のダッシュ条件（周囲0.35に壁なし）も満たせない。

**修正:** 壁に隣接するセルにコスト+2〜4を加え、通路の中央を通るようにする。

### A8. 探索予算切れで経路を捨てる

洞窟や迷路では、240Tick・65,536ノード・1回512ノードの制限に達しやすい。そのとき move_to は失敗する（`NpcSkills.java:1347-1354`）。`Docs/NpcNeoDiamondInvestigation20261026.md` では、水平10ブロックの対象でも `search incomplete` が5件出ている。

**修正:**
- 打ち切り時は、ヒューリスティックで目標に最も近いノードまでの部分経路を返して進む。進みながら探索を続ける。
- 探索中のNPCが1体だけなら、1回の予算を2,048ノードまで上げる。
- 打ち切りの理由（未ロード／時間／ノード数）は結果に分けて記録する。既存資料の要望と同じ。

#### 実施結果（2026-10-26）

- `WalkingPathSearch` で、展開したノードのうち目標に最も近いもの（ヒューリスティック最小）を記録するようにした。`partialPath()` でそこまでの経路を返す。
- `NpcSkills.walking`: 探索が予算切れ（`LIMIT`。ノード数または時間）になったら、部分経路を最大4回まで歩く。歩き終えたら、その位置から再探索する。
  - 未ロード地形による到達不能は、従来どおりその場で止まる。
- JUnit `exhaustedBudgetOffersTheBestPartialRouteTowardTheGoal`: ノード数上限2000で壁を迂回する探索が `LIMIT` になったとき、開始点から目標に近づく部分経路が返ることを確認する。
  - ノード数上限は試験用のコンストラクタで指定する。製品の上限65,536は変えていない。
  - ゲーム内の迷路での試験は未実施。

### A9. 斜め移動・角の条件が厳しい

斜めの移動には、両側の直交セルが同じ高さで立てることを要求する（`WalkingPathSearch.java:95-99`）。さらに `stepClear` はセル中心からAABBを掃引する。そのため、プレイヤーなら通れる角の多くが拒否される。

**修正:** 両側の直交セルについて、体が通る空間があれば立てなくても可とする。または片側だけで可とし、掃引で確認する。

## 作業経路（NpcWorkRoute）との関係

- `NpcWorkRoute` は歩行探索に失敗したときだけ、地形編集を伴う探索（4,096ノード）へ進む。しかし `harmful`（`:333`）は流体を全面禁止しており、水際では編集経路も作れない。
- 上下の範囲は開始点から上20・下24に制限されている（既存資料の3章）。地下からの帰還では、往路の記録を逆にたどる方式を推奨する（既存提案のとおり）。
- 24ノードごとの move_to の分割と、編集1手ごとの move_precisely は、移動の停止と再開を増やす（03のB6）。
