# 03 低速移動と安全への偏り

「安全に傾きすぎて遅い」と見える状態には、3種類の原因が重なっている。

1. 速度の数値そのものが低い（換算の誤り）。
2. ダッシュの条件が厳しすぎ、ほとんどの場面で歩く。
3. 停止→再探索→最終接近（減速）の繰り返しが多い。

1が最も影響が大きく、安全判定とは無関係に常に遅い。

## B1. 速度の換算（最重要）

- 属性は `Player.createAttributes()` をそのまま使う（`bep_3davater_companion.java:167`）。`MOVEMENT_SPEED = 0.1`。
- `NpcStepMoveControl.java:42` は `mob.setSpeed(speedModifier × MOVEMENT_SPEED)` を呼ぶ。
- バニラの `Mob.setSpeed(f)` は速度 `f` を設定し、同時に前進入力 `zza = f` も設定する。移動の加速は「入力 × 速度」なので、**Mobの加速は速度の2乗に比例する**。プレイヤーは入力が約1.0で速度が0.1。
- そのため、プレイヤーと同じ属性値0.1を持つMobは、プレイヤーよりはるかに遅くなる。バニラのゾンビは属性0.23を持つことでこれを補っている。

移動式から推定した値（ゲーム内では未計測）:

| 倍率（使用箇所） | Mobの実効速度 | 推定の秒速 | プレイヤー比 |
| --- | --- | --- | --- |
| 1.6 通常歩行（`TravelPace` / `FollowPace`） | 0.16 | 約1.1ブロック/秒 | 歩行（約4.3）の約26% |
| 2.2 + ダッシュ | 0.286 | 約3.4ブロック/秒 | 歩行の約80%、ダッシュ（約5.6）の約55% |
| 1.0 最終接近・横移動 | 0.10 | 約0.4ブロック/秒 | 約10% |

**修正案（いずれか1つ）:**

- (a) 属性 `MOVEMENT_SPEED` を約0.3にする（`bep_3davater_companion.java:167`）。最も簡単。ただし、属性を参照する他の処理（防具・ポーションの補正、ランク付けモデルの特徴量など）への影響を確認する。
- (b) `TravelPace` / `FollowPace` の倍率を換算する（歩行1.6→約3.2、ダッシュ2.2→約3.6）。
- (c) `NpcStepMoveControl` で「プレイヤー相当の入力1.0 × 属性速度」になるよう `setSpeed` と `setZza` を分けて設定する。プレイヤーと同じ物理になるので最も正確。

**手順:** 先に `getDeltaMovement().horizontalDistance() * 20` を歩行・ダッシュ・最終接近のそれぞれでログに出し、プレイヤーの実測値と比べる。修正後も同じ方法で確認する。

### 実施結果（2026-10-26）

案(c)を実装した。

**変更内容**

- `NpcStepMoveControl.playerInput()`: 地上で移動するときの設定を、プレイヤーと同じ形に変えた。
  - 速度は属性値のまま使う。ダッシュの+30%は `setSprinting` の補正で付く。
  - 前進入力は `min(1, 倍率 / 1.6)` とする。
  - 呼び出し側の倍率の数値は変えていない。通常歩行1.6とダッシュ2.2はプレイヤーと同じ全入力、1.0は入力0.625になる。
- **最終点への減速**: 経路の最後のノード、または直接指定した位置へ向かうときだけ、残り距離に応じて入力を下げる（`max(0.3, 距離/1.2)`）。途中のノードでは減速しない。
- **停止の確認**（`NpcSkills.settling`）: move_to は、水平速度が0.08ブロック/Tick以下になってから到着を報告する。
  - 理由: プレイヤー並みの速度では、入力を止めた後に約0.26ブロック滑る。試験の木では、NPCが自分で作った幅1の階段から落ちた（高さ18→11）。
- **精密移動は従来の速度のまま**: `_arrival` 付きの move_precisely（作業経路の1ブロックごとの編集手順）は、従来の物理のまま動かす。
  - 理由: 速くすると、NPCが作る階段の形が変わる。形によっては降りる経路が見つからなくなり、`tall_tree_builds_walkable_stairs` が約1/25で失敗した。修正前の速度では0/40だった。
  - 階段の作り方（降りられる形の保証）は別の修正とする。
- 水中は変更していない（`NpcWaterTravel.propel` の独自の推進のまま）。

**計測**（新しいGameTest `NpcSpeedGameTests`。平地70ブロックの move_to のうち、区間16〜64の平均）

| | 修正前 | 修正後 | プレイヤー |
| --- | --- | --- | --- |
| 歩行（壁沿いでダッシュ条件を満たさない場合） | 1.126 ブロック/秒（26%） | 4.405 ブロック/秒（102%） | 4.317 |
| ダッシュ | 3.603 ブロック/秒（64%） | 5.727 ブロック/秒（102%） | 5.612 |

推定値（26% / 55〜64%）どおりだった。プレイヤーの値は、通常のブロック上での歩行・ダッシュの基準値。

**回帰**

- NPCのGameTestは132件すべて成功した。全件の実行を2回行い、2回とも成功。
- JUnitは205件で、スキップ15件、失敗0件。
- `tall_tree_builds_walkable_stairs` は単独で30回実行し、30回とも成功した。

**残り**

- B3（ダッシュの開始距離）、B4（`canSprint` の条件）、B5〜B7 は未着手。壁際や起伏では今も歩行速度（プレイヤーの歩行と同じ）にとどまり、ダッシュしない。
- 精密移動の速度、作業経路の階段の形の見直し。

## B2. 低速の個別箇所

| 箇所 | 倍率 | 場面 |
| --- | --- | --- |
| `NpcSkills.java:885` | 1.0 | 残り1.5ブロック以内の最終接近。WorkRouteの24ノード区間ごとにも発生する |
| `NpcSkills.java:868`、`NpcWaterTravel.java:93`、`NpcSkills.java:1396` | 1.2 | 水中 |
| `NpcSkills.java:1090` | 1.1 | 警備位置への復帰 |
| `NpcSkills.java:1275,1277` | 0.8 | ポータルへの歩行 |
| `NpcSkills.java:1431,1458` | 1.0 | 生物を避ける横移動 |

**修正:** B1の換算後、すべて通常歩行の速度に揃える。減速は最後の0.5ブロック以内だけにする。中継点（WorkRouteの区間の終わり）では減速しない。

## B3. ダッシュの開始が遅い

- `TravelPace` / `FollowPace` は、目標まで**8ブロック以上**でダッシュを開始し、4.5ブロックまで継続する（`TravelPace.java:7`、`FollowPace.java:8-9`）。それ未満は1.6で歩く。
- 追従は**6ブロック**を超えるまで動かず、2.5ブロックで止まる（`FollowPace.java:8`）。そのため所有者の後ろで止まっては動くを繰り返す。
- move_precisely はダッシュを禁止している。

**修正:** ダッシュの開始を4〜5ブロックに下げる。追従は3.5ブロックで動き始め2ブロックで止まり、5ブロック超か所有者がダッシュ中ならダッシュする。

## B4. ダッシュ条件 `canSprint` が厳しすぎる

`NpcSkills.java:70-80`:

```java
return npc.foodLevel() > 6
    && !npc.isShiftKeyDown()
    && !npc.isUsingItem()
    && !npc.isInWater()
    && flat   // 次ノードのYが現在のYと完全に一致
    && npc.level().noCollision(npc, npc.getBoundingBox().inflate(.35, 0, .35));
```

- `flat`: 1段でも上り下りがあるとダッシュをやめる。自然地形ではほぼ常に起伏がある。
- `inflate(.35, 0, .35)`: 水平0.35以内にブロックが1つでもあるとダッシュしない。壁際、木の横、フェンス沿い、幅1の通路では常に歩く。02のA7（壁沿いの経路）と組み合わさると、ほとんどの経路でダッシュしない。

**修正:** ±1段の変化は許す（プレイヤーはダッシュしたまま登れる）。0.35の膨張判定はやめ、次の2区間の掃引で衝突しないかを見る。空腹度の条件（>6）はバニラと同じなので残す。

### B3・B4 実施結果（2026-10-26）

**変更内容**

- `canSprint`（`NpcSkills`）を、次の経路ノードへ向かって1ブロック分の体を掃引して判定するように変えた。
  - 掃引の範囲は、段差の高さより上の部分だけにした。
  - 次のノードが1段上なら、掃引を1ブロック持ち上げる。
  - 高さが2以上違うノードではダッシュしない。
  - 従来の「周囲0.35に壁がないこと」「高さが完全に一致すること」の条件はなくした。
  - 空腹度6以下・しゃがみ・アイテム使用中・水中では、従来どおりダッシュしない。
- `TravelPace`: ダッシュの開始を8→5ブロック、終了を4.5→3ブロックにした。
- `FollowPace`: 追従の開始を6→3.5ブロック、停止を2.5→2ブロックにした。ダッシュの開始は8→5ブロック、終了は4.5→3.5ブロック。

**計測**（`NpcSpeedGameTests`）

| --- | --- | --- |
| 壁沿いの直線 | 4.405 ブロック/秒（ダッシュ0/218Tick） | 5.727 ブロック/秒（ダッシュ167/167Tick） |

## B5. 存在しない障害物を避ける横移動

- move_to では `progressTick` が経路の作成時にしか更新されない。
- そのため経路の開始から約20Tick後に `avoidStationaryActor`（`NpcSkills.java:1437`）が発火することがある。条件は「目標への**直線**上、幅1.5の範囲に生物（所有者を含む）がいる」こと。実際の経路上にいるかは見ていない。
- 発火すると移動を止め、速度1.0で最大30Tickの横移動を最大4回行う。

**修正:** `progressTick` を `NpcMoveProgress` の実際の進捗で更新する。発火は「20Tick以上実際に動いていない」かつ「次の経路ノード上に静止した生物がいる」場合に限る。所有者は対象外にする。

### 実施結果（2026-10-26）

**変更内容**

- move_to での発火条件を、`NpcMoveProgress.idleTicks`（新しいセルへの到達も中継点への接近もない時間）が20Tick以上のときに変えた。経路を作ってからの経過時間では判定しない。
- 生物を探す方向を、目標への直線から**次の経路ノードへの方向**に変えた。
- 所有者は対象外にしていない。発火条件が「実際に止まっていて、進む方向にいる」に絞られたため、所有者が通路をふさぐ場合の回避として残した。
- move_to の結果に `actorDetours`（横移動の回数。0のときは省略）を加えた。

**新しいGameTest**（`NpcArrivalGameTests.animals_beside_turning_route_do_not_cause_sidesteps`）

- 配置: 壁の向こう側に牛が5頭いる。目標も壁の向こうにあり、経路は壁沿いに回り込む。
- 修正前: 牛は経路上にいないのに `actorDetours:3`。
- 修正後: 横移動0回で到着する。

**回帰**

- GameTestは139件すべて成功した。全件の実行を2回行い、2回とも成功。
- JUnitは205件で、スキップ15件、失敗0件。
- `tall_tree_builds_walkable_stairs` は15回実行し、15回とも成功した。

**残り**

- 本当に生物にふさがれたときに横移動が働くことを確かめる専用の試験はまだない。

## B6. 停止→探索→再開の繰り返し

- move_to のたびに `navigation.stop()`（`NpcSkills.java:666`）してから新しいA*を始める。探索中（`SEARCHING`）は経路がないので、多くの場合その場で止まる。
- WorkRouteは24ノードごとに move_to を出し直し（`NpcWorkRoute.java:538-551`）、編集1手ごとに1ブロックの move_precisely を出す（`:674`）。
- 02のA1（生物を壁とする判定）による `validAhead` の失敗が、さらに停止を増やす。

**修正:**
- 再探索中は、まだ有効な古い経路を追従し続ける。
- WorkRouteでは、現在の区間が終わる前に次の区間を探索する。または経路全体を一度に渡す。
- 中継点では最終接近の減速を行わない。

## B7. 詰まってから諦めるまでが長い

`NpcMoveProgress.STALL_TICKS = 400`（20秒）。02のA6のとおり、バニラの詰まり回復も働いていない。引っ掛かったNPCは最大20秒立ち止まる。

**修正:** 02のA6の短い詰まり規則（40Tickでジャンプ／再探索）を入れたあと、`STALL_TICKS` を約160（8秒）に下げる。

## B8. 経路上の過剰な安全判定

- 経路のどこかに深さ5を超える水のノードがあると、経路全体を取り消す（`NpcGroundNavigation.java:28-30`）。
- `hazard()` は体の位置にスイートベリーの茂みや粉雪があれば拒否する（`NpcWalkSurface.java:393-401`）。これは妥当だが、コストの加算で足りる場面が多い。
- `NpcWorkRoute.mayBreak` は、どこか1面でも流体に接するブロックを破壊しない（`:390-393`）。湿地やマングローブの木が掘れない。

**方針:** 安全判定は「禁止」と「コスト」に分ける。
- **禁止（コードで保証）:** 溶岩、落下ダメージが出る高さ、窒息する位置、深い水で空気が確保できない経路。
- **コスト（経路で比較）:** 浅い水、茂み、壁際、水に接するブロックの破壊（流れ出す量で評価）。

既存資料の方針「安全性はコードで保証し、モデルは合法な候補間の選好だけを学ぶ」（`NpcArchitectureReview20261025.md`）とも合う。現在は「コスト」にすべき項目まで「禁止」になっており、それが経路なしと低速の両方を生んでいる。
